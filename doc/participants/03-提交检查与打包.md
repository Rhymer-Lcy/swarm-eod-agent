# Swarm-Rescue 提交检查与打包

本文档介绍如何验证并打包你的参赛作品。在提交 zip 包之前，必须通过 `check_submission.sh` 的全部检查。如果你跳过验证直接提交，被评测评委因格式错误拒绝后，将**无法获得该轮成绩**。

---

## 1. 提交目录结构

你只需要准备 `src/swarm_rescue/solutions/` 目录下的文件以及项目根目录的 `req.txt`。最终 zip 包的内容结构如下：

```
team006_preliminary.zip
├── my_drone_eval.py          # 必须：你的无人机控制逻辑
├── team_info.yml             # 必须：队伍信息
├── req.txt                   # 必须：Python 依赖清单
├── image_ref.txt             # 可选：镜像指针，默认空文件
└── (你的其他 .py 文件)        # 可选：你引用的额外模块
```

**关键规则：**

- zip 内部**不允许**出现 `my_drone_eval.py`、`team_info.yml`、`req.txt` 之外的多余目录层级。也就是说，这三个文件必须位于 zip 包的根层级。
- zip 内部**不允许**包含 `swarm_rescue/`、`maps/`、`simulation/`、`config/`、`__pycache__/`、`.venv/`、`launcher.py` 等任何引擎或框架自身文件。
- 模型权重文件（`.pth`、`.pt`、`.ckpt`、`.onnx`、`.h5`、`.pb`、`.safetensors`、`.pkl`、`.pickle`）允许打包，但会增加 zip 体积，需注意大小限制。
- `image_ref.txt` 默认为**空文件**。保持为空 = 按 zip 内的代码评测；填入合法镜像指针 = 按镜像内的 `solutions/` 代码评测，见 [§10 镜像模式](#10-镜像模式可选大型依赖--模型推荐)。

例如，下图是**允许**的本地 solutions/ 目录结构（尚未打包）：

```
src/swarm_rescue/solutions/
├── my_drone_eval.py
├── team_info.yml
├── image_ref.txt             # 可选：默认空文件，保持为空即走代码提交
├── my_drone_rescue_example.py
└── (你添加的其他 .py 文件)
```

## 2. `my_drone_eval.py` 要求

`my_drone_eval.py` 必须定义以下两者**之一**：

### 推荐方式：工厂函数

```python
def drone_class_for_mode(mode: str):
    """根据 mode 返回正确的无人机类。
    mode 为 "rescue"（蓝队）或 "place"（红队）。
    """
    if mode == "rescue":
        return MyRescueDrone
    elif mode == "place":
        return MyPlaceDrone
    # 如果只参加单一项，直接返回对应类即可
```

### 备用方式：直接定义类

```python
class MyDroneEval(YourDroneClass):
    pass
```

如果文件中同时存在 `drone_class_for_mode` 和 `MyDroneEval`，评测评委优先使用 `drone_class_for_mode`。

**检查脚本验证项：**

- 文件必须能通过 Python 语法解析（AST 解析无语法错误）。
- 必须找到 `drone_class_for_mode` 函数定义或 `MyDroneEval` 类定义，否则报错：
  ```
  ERROR: my_drone_eval.py must define drone_class_for_mode(mode) or class MyDroneEval
  ```

## 3. `team_info.yml` 格式

```yaml
team_number: 6
team_name: SkySaviors
team_members: tom, alice, bob, lea
```

**字段要求：**

| 字段 | 类型 | 要求 |
|------|------|------|
| `team_number` | 整数 | 0–999，**必须与 zip 文件名中的队伍编号一致** |
| `team_name` | 字符串 | 非空，队伍名称 |
| `team_members` | 字符串 | 非空，队员姓名列表（逗号分隔） |

**常见错误：**

- `team_number` 写成了字符串（如 `"006"`）→ 必须写为整数 `6`。
- `team_number` 超出 0–999 范围。
- `team_name` 或 `team_members` 为空。
- zip 名是 `team006_preliminary.zip`，但 `team_number: 7` → 不一致，直接拒绝。

## 4. `req.txt` 格式

`req.txt` 位于**项目根目录**（而非 `solutions/` 下），每行一个依赖包名：

```
numpy>=1.24
scipy
opencv-python-headless
```

**规则：**

- 空行和以 `#` 开头的注释行会被忽略。
- 每行只能有一个包名，**不允许**出现文件路径、URL、反斜杠。以下写法会导致错误：

  ```
  ERROR: req.txt line 3: use package names only, not paths or URLs ('./mylib/')
  ERROR: req.txt line 4: one package per line ('numpy scipy')
  ```

- 以 `-` 开头的行（如 `-r`、`--index-url` 等 pip 标志）会产生**警告**，但在大多数情况下不影响通过。建议移除非标准的 pip 标志行。
- **不要固定 `torch` / `torchvision` / `torchaudio` 版本**。评测评委使用 CUDA 12.1 的 PyTorch 预装版本，你在 `req.txt` 中指定的版本会覆盖它，可能导致不兼容。如果一定要用 Torch，可以写 `torch`（不加版本号）或完全省略，系统只会给出一个提醒性警告：

  ```
  WARNING: Submission imports torch; ensure GPU eval runs with --gpus all
  and avoid pinning conflicting torch* versions in req.txt
  ```

- **空 `req.txt` 也是合法的**。如果你的方案没有任何第三方依赖，请保留一个空文件（或仅包含注释），不要删除它，否则会报错：
  ```
  ERROR: req.txt not found: /path/to/project/req.txt
  ```

## 5. 运行 `check_submission.sh` 验证

`check_submission.sh` 是一个**静态分析**脚本，不会运行仿真。它只检查代码结构、语法和 API 使用是否符合比赛规则。

### 两种使用方式

```bash
# 工作区模式：检查当前源代码（在打包之前使用）
./check_submission.sh

# Zip 模式：检查已打包的提交文件（在打包之后使用）
./check_submission.sh team006_preliminary.zip
```

### 检查清单

检查脚本会对你的提交执行以下所有检查：

| 检查项 | 类型 | 说明 |
|--------|------|------|
| 必需文件存在 | 错误 | `my_drone_eval.py`、`team_info.yml`、`req.txt` 缺一不可 |
| 文件名合规 | 错误 | zip 名必须是 `teamNNN_{step}.zip` 格式（step ∈ `preliminary`, `semifinal`, `final`） |
| `team_info.yml` 合法 | 错误 | 三个字段完整、`team_number` 与 zip 名一致且合法 |
| `my_drone_eval.py` 入口 | 错误 | 必须定义 `drone_class_for_mode()` 或 `MyDroneEval` |
| 禁止的目录/文件 | 错误 | 不得包含 `.venv/`、`__pycache__/`、`swarm_rescue/`、`maps/`、`simulation/`、`config/`、`launcher.py` 等 |
| API 命名 | 错误 | 只能使用当前命名（`Bomb`、`DisposalCenter`、`grasped_bombs()` 等）；`WoundedPerson`、`RescueCenter`、`WOUNDED_PERSON`、`RESCUE_CENTER`、`grasped_wounded_persons` 一律被拒绝 |
| 地面真值 API 调用 | 错误 | 不得在任何函数中调用 `true_position()`、`true_angle()`、`true_velocity()`、`true_angular_velocity()` |
| `control()` 内禁用属性 | 错误 | `control()` 方法中不得直接访问 `self.position`、`self.angle`、`self.velocity`、`self.angular_velocity` |
| `req.txt` 格式 | 错误 | 不允许路径、URL、一行多包名 |
| 文件嵌套层级 | 错误 | `my_drone_eval.py` 等必需文件必须在 zip 根目录，不能位于子文件夹内 |
| `image_ref.txt` 格式 | 错误 | 若存在且非空，必须是合法的镜像引用（`[registry/]repo[:tag][@sha256:...]`）、只能一行、必须位于 zip 根目录 |
| `print()` 调用过多 | 警告 | 超过 15 次 `print()` 调用时提醒减少控制台输出 |
| 调试 UI 调用 | 警告 | 检测到 `cv2.imshow()` / `cv2.waitKey()` 时提醒关闭调试代码 |
| 引入 torch | 警告 | 检测到 `import torch` 时提醒注意 GPU 配置和版本冲突 |
| zip 文件过大 | 警告 | 纯代码 >500 KiB 或含模型 >30 MiB 时提醒；超过 100 MiB 时发出严重警告 |

### 错误列表（导致拒绝）

以下每一条都会导致 `check_submission.sh` 返回失败（非零退出码），**必须全部修复后再提交**：

1. **缺少必需文件**：zip 包内找不到 `my_drone_eval.py`、`team_info.yml` 或 `req.txt`。
2. **无有效入口**：`my_drone_eval.py` 没有定义 `drone_class_for_mode` 函数也没有 `MyDroneEval` 类。
3. **使用无效 API 名**：源码中包含 `WoundedPerson`、`RescueCenter`、`WOUNDED_PERSON`、`RESCUE_CENTER`、`grasped_wounded_persons`、`number_wounded_persons`、`"type": "rescue_center"` 等名称。
4. **调用地面真值 API**：在函数体（包括 `__init__`）内调用了 `true_position()`、`true_angle()`、`true_velocity()`、`true_angular_velocity()`。
5. **`control()` 内访问 `self.*` 真值**：在名为 `control` 的方法中直接访问 `self.position`、`self.angle`、`self.velocity`、`self.angular_velocity`。比赛模式下这些属性被禁用，必须使用 `measured_gps_position()` 和 `measured_compass_angle()` 等传感器 API。
6. **包含禁止路径**：zip 内有 `__pycache__/`、`.venv/`、`.git/`、`node_modules/`、`swarm_rescue/`、`maps/`、`simulation/`、`config/` 或 `launcher.py`。
7. **`team_info.yml` 无效**：字段缺失、team_number 不合法，或 team_number 与 zip 文件名中的编号不一致。
8. **zip 命名不符**：文件名不符合 `teamNNN_{preliminary,semifinal,final}.zip` 格式——注意队伍编号**必须是三位数字（不足三位需补零）**，如 `team006` 而非 `team6`。

### 警告列表（提醒但不拒绝）

以下警告**不会导致检查失败**，但建议在提交前处理：

1. **超过 15 个 `print()` 调用**：评测时大量打印会影响日志可读性，建议精简。
2. **检测到 `imshow()` / `waitKey()` 调试 UI**：比赛环境通常无图形界面，这些调用会导致运行异常，请删除或注释掉。
3. **导入了 `torch`**：提醒你确保评测评委已配置 GPU（`--gpus all`），同时不要在 `req.txt` 中固定 torch 版本。
4. **zip 文件偏大**：纯代码超过 ~500 KiB、含模型文件超过 ~30 MiB 时提示；超过 100 MiB 时给出严重警告。常见原因是误把 `.venv` 或 `swarm_rescue/` 打进了包里。
5. **启用了镜像模式**：`image_ref.txt` 非空时提示评测将运行镜像内的 `solutions/`，zip 里的 Python 代码会被忽略。

### 典型检查输出示例

```
# 通过
$ ./check_submission.sh team006_preliminary.zip
Submission check passed.

# 未通过（有多种错误）
$ ./check_submission.sh team006_preliminary.zip
ERROR: Zip file name must match teamNNN_{preliminary,semifinal,final}.zip ...
ERROR: req.txt line 3: use package names only, not paths or URLs ('./mylib/')
WARNING: Found 28 print() calls in submission code; ...
Submission check failed.
```

## 6. `create_zip_submission.sh` 自动打包

项目提供了自动打包脚本，按交互式提示逐步操作：

```bash
./create_zip_submission.sh
```

### 交互流程

**步骤 1：前提检查**  
脚本自动检查 `src/swarm_rescue/solutions/my_drone_eval.py`、`src/swarm_rescue/solutions/team_info.yml` 和 `req.txt` 是否存在。任一缺失则退出。

**步骤 2：确认队伍信息**  
脚本从 `team_info.yml` 中提取信息并展示：

```
Team number: 006
Team name: SkySaviors
Team members: tom, alice, bob, lea
Do you confirm this information? (y/n)
```

输入 `y` 继续；输入其他内容则退出，提示你修改 `team_info.yml` 后重新运行。

**步骤 3：选择评测阶段**  
```
Please choose an evaluation step from the following options (a, b, or c):
a) preliminary
b) semifinal
c) final
```

输入 `a`、`b` 或 `c`。输入其他字符则退出。

**步骤 4：生成 zip**  

- 将 `src/swarm_rescue/solutions/` 下的**所有文件**打成 zip（使用 `zip -r`，不额外创建文件夹层级，即 zip 内的文件在根目录下）。
- 将 `req.txt` 追加到 zip 根目录中。
- 输出文件名如 `team006_preliminary.zip`。

```
Create the ZIP file team006_preliminary.zip:
  adding: my_drone_eval.py (deflated 62%)
  adding: team_info.yml (deflated 22%)
  adding: my_drone_rescue_example.py (deflated 65%)
  adding: req.txt (stored 0%)

Please send the file team006_preliminary.zip to your evaluator.
```

如果同名 zip 文件已存在，会先删除再重新创建。

## 7. 手动创建 zip（替代方案）

如果无法使用 `create_zip_submission.sh`，也可以手动打包。**关键是要保证 zip 内文件在根层级**：

```bash
# 第一步：打包 solutions/ 目录下的所有文件
cd src/swarm_rescue/solutions && zip -r ../../../team006_preliminary.zip .

# 第二步：回到项目根目录，追加 req.txt
cd ../../.. && zip -u team006_preliminary.zip req.txt
```

**常见手动打包错误：**

- 在 `src/swarm_rescue/` 目录下执行 `zip -r team006_preliminary.zip solutions/` → 导致 zip 内多了 `solutions/` 文件夹，必需文件不在根层级。
- 忘记打 `req.txt` → 检查脚本直接报错缺少必需文件。
- `cd src/swarm_rescue/solutions && zip -r ... *` → 可能遗漏隐藏文件（虽然通常不需要），用 `.` 更安全。

打包之后用以下命令检查 zip 内部结构：

```bash
unzip -l team006_preliminary.zip
```

输出应该是：

```
  Length      Date    Time    Name
---------  ---------- -----   ----
     1234  2024-01-01 12:00   my_drone_eval.py
       76  2024-01-01 12:00   team_info.yml
        0  2024-01-01 12:00   req.txt
     2345  2024-01-01 12:00   my_drone_rescue_example.py
---------                     -------
     3655                     4 files
```

确认**没有** `solutions/my_drone_eval.py` 这种嵌套路径。

## 8. 提交流程总结

从头到尾的完整提交流程：

```
1. 开发
   在 src/swarm_rescue/solutions/ 中编写你的无人机控制代码。

2. 本地自测（比赛模式）
   .venv/bin/python -m swarm_rescue.launcher --competition -c config/competition_rescue_eval_plan.yml
   比赛模式会禁用地面真值 API，确保你的代码可以在评测环境中正常运行。

3. 静态检查
   ./check_submission.sh
   → 修复所有 ERROR，关注所有 WARNING。

4. 打包
   ./create_zip_submission.sh
   → 按提示确认信息并选择阶段，生成 teamNNN_step.zip。

5. 验证 zip
   ./check_submission.sh team006_preliminary.zip
   → 确认输出 "Submission check passed."

6. 提交
   将 team006_preliminary.zip 发送给评测评委。
```

> **重要提醒：** `check_submission.sh` 通过 ≠ 代码在评测中能正常工作。静态检查只验证代码结构和 API 合规性，不验证运行时的逻辑正确性。请务必在 `--competition` 模式下完整运行一次仿真后再提交。

## 9. 常见问题

### Q: `check_submission.sh` 通过了，但我的代码运行时崩了？

静态检查只做 AST 分析和文件结构验证，**不会运行仿真**。如果你的代码在 `--competition` 模式下使用了 `self.position` 而 `self.position` 恰好没有被 AST 直接检测到（比如通过 `getattr(self, "position")` 间接访问），检查脚本查不出来，但运行时会触发禁用错误。请在实际仿真中充分测试。

### Q: 我能带模型权重文件吗？

可以。`.pth`、`.pt`、`.ckpt`、`.onnx`、`.h5`、`.pb`、`.safetensors`、`.pkl`、`.pickle` 等模型权重文件是允许的，不会导致检查失败。但要注意：

- 权重文件的 zip 大小软警告线是 30 MiB（纯代码是 500 KiB）。
- 100 MiB 以上会再发一条严重警告。
- 如果文件超过 10 MiB 但不是模型权重格式，会产生警告（提示你可能误打了 `.venv`）。

### Q: 我在 solutions/ 下放了好多辅助 .py 文件，要紧吗？

没问题。`solutions/` 下的所有 `.py` 文件都会被 `create_zip_submission.sh` 自动打包，也会被检查脚本扫描（检查废弃 API、地面真值调用等）。只要它们不违规就行。

### Q: zip 文件名里队伍编号必须三位吗？

是的。`teamNNN` 的 `NNN` 必须是三位数字，不足三位补零。如队伍编号 6 对应 `team006`，队伍编号 42 对应 `team042`。`team6_preliminary.zip` 不符合正则表达式，会被拒绝。

### Q: `req.txt` 放在哪里？

`req.txt` 必须放在**项目根目录**（与 `src/`、`check_submission.sh` 同级）。打包后它位于 zip 的根层级，不能嵌套在任何子文件夹下。

### Q: 我不用第三方库，`req.txt` 能空着吗？

可以。保留一个空白文件或仅包含注释即可，但**不能删除这个文件**。

### Q: `check_submission.sh` 报 `python3: command not found`？

在项目根目录执行：
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install --editable .
```
然后重新运行 `./check_submission.sh`。它优先使用 `.venv/bin/python`。

### Q: 能提交 `.pyc` 或 `__pycache__/` 吗？

**不能。** `__pycache__/` 在禁止列表里，会导致 ERROR。`create_zip_submission.sh` 不会主动包含这些文件，但如果是手动打包请确保不包含它们。

### Q: 为什么我的代码里写 `WoundedPerson` 会被拒？

以下名称会被 `check_submission.sh` 直接拒绝，请使用右侧的当前命名：

| 会被拒绝的名称 | 当前命名 |
|------|------|
| `WoundedPerson` | `Bomb` |
| `RescueCenter` | `DisposalCenter` |
| `TypeEntity.WOUNDED_PERSON` | `TypeEntity.BOMB` |
| `TypeEntity.RESCUE_CENTER` | `TypeEntity.DISPOSAL_CENTER` |
| `grasped_wounded_persons()` | `grasped_bombs()` |
| `'type': 'rescue_center'` | `'type': 'disposal_center'` |

## 10. 镜像模式（可选，大型依赖 / 模型推荐）

如果你的方案需要**体积很大的依赖或模型**（例如自己训练的权重、体积超出 zip 限制的第三方包），可以把运行环境做成 Docker 镜像提交，用镜像代替 zip 传代码。

> 主办方发布的官方基础镜像以 **tar.gz 离线包**分发（文件名与校验值**以主办方最终公告为准**，例如 `swarm-rescue-base-v1.tar.gz` + `.sha256`）。拿到后用 `docker load` 载入本地即可，**不需要从任何仓库拉取**；所有选手镜像必须基于它构建。载入方式见 [10.5](#105-构建与提交步骤)。

### 10.1 判定规则

评测端读取 `image_ref.txt`：

| `image_ref.txt` 内容 | 评测行为 |
|----------------------|----------|
| 空文件（默认） | 使用 zip 内的代码，按 `req.txt` 安装依赖 |
| 合法的镜像指针 | 拉取该镜像，**使用镜像内 `/app/src/swarm_rescue/solutions/` 的代码**；zip 里的 `.py` 代码和 `req.txt` 都会被忽略 |

### 10.2 硬性要求

1. **必须基于官方基础镜像构建**：Dockerfile 的 `FROM` 必须是从官方 tar.gz 载入的那个镜像（`docker load` 后可用 `docker images` 看到它的名字与 tag）。评测端会逐层比对官方镜像的层，一旦发现官方层被改动（或根本不是从官方镜像构建的），该次提交判为 `invalid_input`。
2. **必须是 x86-64**：评测平台是 `linux/amd64`，Apple Silicon / ARM 机器上务必显式指定平台：
   ```bash
   docker buildx build --platform linux/amd64 -t <你的仓库>/team006:v1 --push .
   ```
3. **zip 里必须保留三个必需文件**（`my_drone_eval.py`、`team_info.yml`、`req.txt`），作为校验、审计与代码备份。**队伍身份一律以 zip 为准**：zip 文件名里的 `teamNNN` 是队伍的正式编号（评测结果目录与其中的产物文件名都用它），队伍名称与成员也取自 zip 里的 `team_info.yml`；镜像内的那份只在你于镜像内单独跑 `launcher.py` 时才有意义。
4. 建议用 **digest 固定**镜像（`repo@sha256:...`）；评测端会把实际解析到的 digest 记录在评测结果里。

### 10.3 镜像内环境

项目源码在镜像内的位置：

| 路径 | 说明 |
|------|------|
| `/app/src/swarm_rescue/` | 项目源码目录 |
| `/usr/local/lib/python3.11/site-packages/swarm_rescue/` | 安装后的包副本 |

`/app/src/swarm_rescue/` 的目录结构：

```text
/app/src/swarm_rescue/
├── __init__.py
├── launcher.py          # 本地单队评测入口
├── simulation/          # 仿真器核心（传感器、无人机、地图、渲染）
├── maps/                # 地图与地图工具
├── resources/           # 贴图等资源
├── tools/               # 辅助工具
└── solutions/           # ← 唯一由你掌握的目录，评测时从这里加载代码
    ├── my_drone_eval.py # 必需：返回对应模式的无人机类
    └── (你的其他文件与子目录，例如模型权重)
```

> `team_info.yml` 与 `image_ref.txt` 属于 **zip 侧**；镜像里带着也行（方便你在镜像内直接跑 `launcher.py`），评测时以 zip 的那份为准。

**Python 环境**：Python 3.11，已预装项目依赖（fpdf、opencv-contrib-python、pandas、arcade、cerberus、scikit-image、matplotlib、PyYAML、numpy、pyqtgraph、PySide6）。

`/app/src/swarm_rescue/solutions/` 在评测开始前会被交给评测进程的运行用户，因此**你的代码可以在这个目录下写日志、缓存等文件**（`logging.FileHandler`、`os.makedirs(...)` 之类的写法都能用），不需要在 Dockerfile 里手动 `chmod`。评测时容器统一以非 root 用户运行，Dockerfile 里的 `USER` 不影响评测。

> 基础镜像**不包含 PyTorch**。仿真器的 GPU 加速走 OpenGL 4.4 / GLSL 4.40（镜像内已提供 mesa 相关库），与 CUDA 无关。

### 10.4 哪些代码不能动

**除 `solutions/` 之外的所有源码都属于评测框架，一律不得修改**，包括但不限于：

- `simulation/` —— 仿真器核心（传感器模型、噪声、无人机动力学、渲染）
- `launcher.py`、`maps/`、`resources/`、`tools/`
- `site-packages/swarm_rescue/` 下的任何文件

评测时的实际行为：

- 框架代码由评测机从组委会自己的仓库**只读挂载**进容器，只有 `solutions/` 来自你的镜像；
- 因此你在镜像里对框架代码的改动**评测时不会生效**；
- 同时会被层比对检查发现，**该次提交直接判为 `invalid_input`**（评测失败，且不影响其他队伍）。

> 结论：**只往 `solutions/` 里放东西，不要动框架。** 乱改框架 = 评测失败。

### 10.5 构建与提交步骤

```bash
# 1. 载入官方基础镜像（从主办方给的 tar.gz，不需要 pull）
sha256sum -c swarm-rescue-base-v1.tar.gz.sha256     # 可选：先校验
docker load -i swarm-rescue-base-v1.tar.gz
docker images | grep swarm-rescue-base              # 确认名字与 tag，例如 swarm-rescue-base:v1
docker image inspect swarm-rescue-base:v1 --format '{{.Architecture}}'   # 必须是 amd64

# 2. 编写 Dockerfile：把方案代码放到约定目录
cat > Dockerfile.submit <<'EOF'
FROM swarm-rescue-base:v1
COPY src/swarm_rescue/solutions/ /app/src/swarm_rescue/solutions/
EOF

# 3. 构建并推送（务必指定 linux/amd64）
docker buildx build --platform linux/amd64 \
    -f Dockerfile.submit \
    -t <你的仓库>/team006:v1 --push .

# 4. 写入镜像指针
echo "<你的仓库>/team006:v1" > src/swarm_rescue/solutions/image_ref.txt

# 5. 校验并打包（与普通提交完全相同）
./check_submission.sh
./create_zip_submission.sh
./check_submission.sh team006_final.zip
```

> 只有**基础镜像**是离线分发的；**你交付的镜像仍然要推到一个评测机能直接拉取的仓库**（第 3 步的 `--push` 与第 4 步的指针缺一不可）。
>
> 基础镜像不必改名：`docker load` 后的 `REPOSITORY:TAG` 就是 `Dockerfile` 里 `FROM` 该写的内容。（你也可以把它 `docker tag` 成自己仓库的名字再推上去，这样推送派生镜像时能复用基础层、少传数据；不推也完全可以——评测端只比对层，不关心名字。）

### 10.6 失败语义

镜像模式下的失败**只影响你自己的队伍**，不会影响其他队伍，也不会中断整批评测：

| 情况 | 结果 |
|------|------|
| 提交镜像拉取失败（地址错误 / 仓库不可访问 / 需要登录） | `invalid_input` |
| 提交镜像架构不是 `amd64` | `invalid_input` |
| 官方镜像层被改动 / 不是从官方镜像构建 | `invalid_input` |
| 镜像内找不到 `/app/src/swarm_rescue/solutions/` 或入口不合法 | 评测失败 |

> 评测机需要能直接拉取**你提交的那个镜像**。**不要放在需要交互式登录的私有仓库**；若必须私有，请提前把只读凭证提供给出题方。

### 10.7 常见问题

**Q: `image_ref.txt` 需要删掉吗？**

不需要，保持为空文件即可，此时按 zip 内的代码评测。

**Q: 我填了镜像指针，`req.txt` 还要写吗？**

文件必须存在（校验要求），但镜像模式下它不生效，内容留空即可。

**Q: 我本地是 Apple Silicon，构建出来的镜像能用吗？**

不能直接用，必须 `docker buildx build --platform linux/amd64`，否则评测时判 `invalid_input`。

**Q: 基础镜像要 `docker pull` 吗？**

不需要，也从任何仓库都拉不到：主办方以 tar.gz 离线包分发，`docker load -i swarm-rescue-base-v1.tar.gz` 载入即可。载入后 `docker images` 里看到的 `REPOSITORY:TAG`（例如 `swarm-rescue-base:v1`）就是 `Dockerfile` 里 `FROM` 要写的名字。

**Q: 我能在基础镜像上再装东西吗？**

可以，`RUN pip install ...`、`COPY` 自己训练的权重都可以——加层不影响校验，校验只要求**官方那几层没被改动**。
